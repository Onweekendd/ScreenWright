# 画布操作协议合并方案（canvas_ops）

> 状态：已实施（四步均已提交，见 `git log --grep=canvas_ops`）。`SuspendType` 由 31 个降到 10 个。

## 1. 为什么要改

agent 改画布走的是「工具挂起 → 前端执行 → 带回执恢复 → 后端过 core 落盘」。现在每种操作各有一套协议：

- `SuspendType` 共 31 个，其中 22 个是「11 种画布写操作 × 审批 / 自动两种模式」。
- 每种操作要写三处：后端定义挂起类型并按模式挑类型、读专属回执字段；前端写处理函数（审批版基本是「弹确认 + 调自动版」）；
  评测假前端（`evals/harness/fake-frontend.ts`）再映射一遍。
- 回执字段各叫各的：`moved` / `ungrouped` / `filterSaved` / `componentUpdated` / `screenInfoUpdated`……
- 组件 id 有的是字符串、有的是数字，前端到处 `Number(id)`。
  实际出过的 bug：move_component 把入参 `"5_1/114"` 原样交给前端，`Number()` 成了 NaN（group_component 那套转了，这套漏了）。

## 2. 目标

一个挂起类型 `canvas_ops` 承载所有画布写操作：

- 审批 / 自动只在一处判断（外层可选的 `approval`），不再一种操作两个类型；
- 前端一个执行器 + 每种操作一个小函数，审批、写入排队、出错处理只写一遍；
- 组件 id 在协议里一律是 `number`，后端没解析好编译不过；
- 回执统一成 `ok` / `error`。

**模型侧不变**：各工具（`create_component`、`move_component`……）的入参和描述都不动，`canvas_ops` 只在前后端之间。

不并进来的（不是画布写入）：`ask_user_question`、`enter_plan_mode`、`submit_plan`、`capture_canvas`、
`save_ai_template`、`apply_ai_template`、`execute_in_browser`、edit_files 普通文件的纯审批 `ask_approval`。

## 3. 协议

```ts
// servers/server/src/mastra/types/suspend.ts

const CanvasOpSchema = z.discriminatedUnion("op", [
  z.object({ op: z.literal("create_component"), component: z.record(z.string(), z.unknown()), placement: placementSchema }),
  z.object({ op: z.literal("copy_component"), component: z.record(z.string(), z.unknown()), placement: placementSchema }),
  z.object({ op: z.literal("delete_component"), componentId: z.number(), placement: placementSchema }),
  z.object({ op: z.literal("update_component"), component: ComponentSchema }),
  z.object({ op: z.literal("group_components"), componentIds: z.array(z.number()).min(2) }),
  z.object({ op: z.literal("ungroup"), groupIds: z.array(z.number()).min(1) }),
  z.object({ op: z.literal("move_components"), componentIds: z.array(z.number()).min(1), target: moveTargetSchema.optional() }),
  z.object({ op: z.literal("add_panel_state"), panelId: z.number(), stateName: z.string() }),
  z.object({ op: z.literal("save_filter"), filter: FilterSchema, originalName: z.string().optional() }),
  z.object({ op: z.literal("delete_filter"), filterName: z.string() }),
  z.object({ op: z.literal("update_screen_info"), screenId: z.number(), detail: LargeScreenDetailInfoSchema,
             minioIds: z.array(z.union([z.number(), z.null()])).optional() })
]);

/** 成功时带上前端才拿得到的产物：新组件（含业务接口分配的真实 id）、新面板状态（画布上已用的 uuid） */
const OpResultSchema = z.union([
  z.object({ ok: z.literal(true), component: z.record(z.string(), z.unknown()).optional(),
             state: z.record(z.string(), z.unknown()).optional() }),
  z.object({ ok: z.literal(false), error: z.string() })
]);

[SuspendType.CanvasOps]: {
  suspend: z.object({
    type: z.literal(SuspendType.CanvasOps),
    approval: z.object({ purpose: z.string() }).optional(), // 有它：前端先弹一次确认，整批一次
    ops: z.array(CanvasOpSchema).min(1),
    ...batchOperationFields                                // edit_files 多轮对账用，原样带回
  }),
  resume: z.union([
    z.object({ approved: z.literal(false), ...batchOperationFields }),
    z.object({ results: z.array(OpResultSchema), ...batchOperationFields }) // results[i] 对应 ops[i]
  ])
}
```

约定：

- `results` 与 `ops` **按下标一一对应**，长度相等。单个操作失败只记在自己那一项，不中断同批后面的。
- 前端整批放进**一次** `enqueueCanvasMutation`（批内有先后依赖，不能被别的 tab 插进来）；
  审批的 `confirm` 在入队之前（等审批不能卡住别的 tab 的写入，和现在一致）。
- `create_component` 现在靠 `index` 把回执对回入参（校验没过的项不发给前端，两边长度不一致）。
  改成 `ops` 后由后端自己记「第 i 个 op 对应入参第几项」，协议里不再需要 `index`。

## 4. 后端

新增 `servers/server/src/mastra/tools/canvas-ops.ts`：

```ts
/** 按模式决定要不要审批，挂起交给前端。各工具不再自己判断 AgentMode、不再挑挂起类型 */
export function suspendCanvasOps(context, { purpose, ops, batch? }): never;

/** 读回执：用户拒绝返回 { rejected: true }；否则校验长度与 ops 一致，按下标取结果 */
export function readCanvasOpResults(resumeData, expectedCount): { rejected: true } | { results: OpResult[] };
```

各工具改成：首次执行时组装 `ops` → `suspendCanvasOps`；恢复时 `readCanvasOpResults` → 按结果过 core 落盘（落盘逻辑不变）。

- **id 归一放在组装 ops 那一步**：入参 `"5_1/114"` → 定位文件 → 从文件名取数字 id。schema 是 `z.number()`，漏了就编译不过。
- edit_files 的同步处理器（`sync-handlers/*.ts` 里的 `askOrPush`）改成产出一个 op，审批由 `needsApproval` 决定是否带 `approval`。
- `resume-mode.ts` / `resume-termination.ts` 只认计划模式两个类型，不受影响。

## 5. 前端

新增 `apps/app/src/views/build/components/agentBI/hooks/canvasOps.ts`：

```ts
const opHandlers: { [K in CanvasOp["op"]]: (op: Extract<CanvasOp, { op: K }>) => Promise<OpResult> } = {
  create_component: ...,   // 现 createComponentItems 里单项那段
  move_components: ...,    // 现 handleMoveComponent 的主体，去掉 Number(id)
  ...
};

export const handleCanvasOps: SuspendHandlerFn<SuspendType.CanvasOps> = async (info) => {
  const { approval, ops } = info.suspendPayload;
  if (approval && !(await confirm(sessionId, `是否允许：${approval.purpose}？`))) {
    return { approved: false, ...batchFields };
  }
  return enqueueCanvasMutation(async () => {
    const results = [];
    for (const op of ops) {
      try { results.push(await opHandlers[op.op](op as never)); }
      catch (e) { results.push({ ok: false, error: (e as Error).message }); }
    }
    return { results, ...batchFields };
  });
};
```

`useComponentStreamUpdater.ts` 里对应的 22 个处理函数删掉，`suspendHandlers` 只注册一个 `canvas_ops`。
各操作的实际执行逻辑（`createComponent`、`moveComponents`、`handleSelectGroupAction`……）原样复用，只是搬家。

- **假前端**：`evals/harness/fake-frontend.ts` 的映射表要跟着改成按 `op` 分发，否则评测全挂。

## 8. 这次不做、以后容易做的

- edit_files 多个文件合成一轮 `canvas_ops`，一次确认（现在一个文件挂起一轮）。
- 同一批 `ops` 作为一个撤销单元。
- 对照参考：[infinite-canvas](https://github.com/basketikun/infinite-canvas) 的 `canvas_apply_ops`——
  所有便捷工具先翻译成 ops，再走同一个写入口（`canvas-agent/src/canvas/operations.ts`）。

## 9. 实施记录（和上面方案的出入）

- **`readCanvasOpResults` 的返回**：不是 `{ rejected } | { results }`，而是 `{ status: "pending" | "rejected" | "done" | "invalid" }`。
  `pending` = 还没有回执（首次执行）；`invalid` = 回执条数和发出去的 op 数对不上，工具直接把原因还给 agent，不按下标取。
  不传 `expectedCount` 就不校验长度——create_component 要先看一眼回执再决定怎么对账。
- **载荷组装拆出了 `canvasOpsPayload`**：`suspendCanvasOps` 里调它；edit_files 的同步处理器只产出载荷、
  由调用方补批次字段再挂起，也走它。ASK / AUTO 在这一处判断。
- **协议里没有的字段**：旧载荷里的 `replacements`（前端从不读它）、`filterName`（就是 `filter.name`）、
  `index`（create_component 的下标）都不再下发。
- **create_component 的对账**：ops 只含准备阶段通过的项。恢复时回执条数等于入参条数 → 整批都发出去了，直接按顺序对回，
  不再读库重算模板；条数更少 → 有项在准备阶段被拦下，重算一遍才知道是哪几项、什么原因。
- **删除组件的审批文案**：协议里只有 `approval.purpose`，所以后端读工作区里的组件 json 取名字拼进去
  （`删除组件「分组」`），前端不再按 id 去画布上查名字。
- **先写工作区、再推前端的三个工具**（configure_component_data、configure_callback_args、createEventTemplate）：
  用户在 ASK 模式拒绝时，旧实现因为回执里没有 `componentUpdated` 会**重新跑一遍并再次挂起**；
  现在直接抛「用户拒绝……工作区已写入、画布未应用，两边暂时不一致」。真正的修法是把它们也改成
  edit_files 那种「前端成功后才落盘」，这次没动（落盘逻辑不变是约束）。
- **eval**：`isWriteSuspend` / `isAutoWriteSuspend` 改成按 `canvas_ops` 及其 `approval` 判断，入参是整条挂起记录而不是类型名；
  新增 `describeSuspend`，流水账里显示 `canvas_ops[move_components,ungroup]+approval` 而不是清一色 `canvas_ops`。
- **没动**：`streamReplayIntegration.test.ts` 回放的是一份历史录制（挂起类型是 `ask_approval_create_component`），
  它只验证流的分发，不依赖前端注册表里真有这个类型，所以保留。
